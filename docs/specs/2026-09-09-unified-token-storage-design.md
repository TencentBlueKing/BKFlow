# Token 授权统一存储与自动迁移

日期：2026-09-09

基线：`660f2005c7087db647c980cc68043611d469ad99`；关联 [PR #913](https://github.com/TencentBlueKing/BKFlow/pull/913)、TAPD `138057563`。

用户已选择统一授权存储，并确认存量 Token 数据量较小，发布时默认迁移的风险可控。本设计替代原组合 Token 设计中的双存储方案和发布迁移步骤；其他已确认接口、权限与生命周期约束继续适用。

## 1. 最终模型

- `Token` 只保留票据主键、空间、用户、有效期及授权集合摘要。删除 `resource_type`、`resource_id`、`permission_type` 和依赖它们的旧索引。
- `TokenGrant` 是所有票据的唯一授权来源。单项票据有一条明细，组合票据有多条明细；不再区分历史字段与新明细的读取路径。
- 所有有效票据都具有非空的 `grant_set_hash`。它是完整授权集合的索引摘要和完整性校验值，不承载另一份资源授权。数据库字段非 NULL，算法继续使用现有 v1 规范 JSON 和 SHA-256。
- `is_composite` 仅表示有效授权集合有两项及以上，不再由摘要是否为空决定。单项 SCOPE 的旧内部目标类型回退仍保留；多项票据仍必须提供明确目标类型。HTTP 消费者继续提供目标类型。
- 明细缺失、重复或摘要不匹配时整票据无效。单项也执行完整性校验。后台管理展示明细并预取数据，明细和摘要不可独立编辑；不提供无法创建有效授权集合的主记录新增入口。

## 2. 存量迁移

保留已经提交的 `0001` 到 `0005` 迁移，追加独立数据迁移及 Django 生成的结构清理迁移。发布执行普通 `migrate` 即按依赖顺序完成以下步骤，无需另行运行命令：

1. 使用历史模型和当前数据库 alias，在数据事务中锁定/读取票据；旧服务写入已经暂停。
2. 对 `grant_set_hash IS NULL` 的历史单项票据，以主表原三个字段为权威数据，创建恰好一条明细并计算集合摘要。即使有过期记录、已删除资源、资源 ID 前导零、Unicode 或大小写差异，也原样搬迁。意外存在的旧单项明细不得被合并授权。
   - 三个旧资源字段全部为空时，在任何数据变更前中止迁移。该形态无法与损坏的组合历史可靠区分，不能静默转换为有效单项。
   - 未知枚举或仅部分字段为空时仍按数据库原值搬迁，不进行权限修复或枚举归一化；新版本运行时会对非法明细保持 fail-closed。
3. 对已有组合票据保留现有主键、摘要和明细，不重新计算摘要来修复损坏的授权。完整性异常中止迁移；不得把缺失明细的原组合票据降成有效单项。
4. 校验每张原单项票据的唯一明细和摘要与原字段完全一致，主键、用户、空间及有效期完全不变；验证已有组合集合仍完整。错误发生在数据迁移内部，旧字段清理不会执行。错误信息不打印 bearer token 值。
5. 结构迁移将集合摘要改为非 NULL，并移除三个旧授权字段和旧复合索引。结构操作必须来自 `makemigrations`，不手写 DDL 或修改已有迁移。

数据迁移的 v1 摘要实现冻结在迁移中，不导入运行时模型/服务。数据量较小，允许遍历全部票据；所有状态都迁移，不额外延长有效期、不重签、不清理旧记录。迁移不调用引擎或外部资源服务。

反向迁移到 `0005` 时，先由结构迁移重建旧列，再在数据迁移的反向函数中把有效单项明细还原到三个字段、摘要置 NULL并删除该单项明细；多项仍保持 `0005` 的组合存储。已有与新签发单项都可还原，不改变票据身份/有效期。损坏数据中止反向操作。回退到不支持组合票据的旧二进制之前，仍须先使组合票据失效；不宣称任意旧版本可直接读取新结构。

## 3. 运行时与旧协议

- `issue_token(space_id, user, grants, expiration_seconds, auto_renewal)` 对单项和组合使用同一套完整集合摘要检索、持锁复查、最晚有效期复用和主表/全部明细原子写入。子集与超集不得互相复用。
- `Token.get_grants()` 只读明细。`Token.to_json()` 为有效单项明细重建原成功响应的 `resource_type`、`resource_id`；不新增原来没有的 `permission_type` 或 `grants`。多项不得假装成某一个单项响应。
- 资源撤销过滤和 auth 汇总都只查询明细；多个资源条件必须落在同一条明细内，主票据按原规则去重计数，已过期记录仍计入原撤销计数。
- 用户、空间、到期、整集合完整性、任务祖先、MOCK、scope、FLOW_* 投影和旧响应时间编码保持原批准实现的行为。
- 原始 grants 1–32 项、旧字段优先、全部校验后才写入、整票据撤销、续期不能复活撤销票据等约束不变。新 grants 申请默认开启，显式 false 可关闭。
- 不增加接口、请求字段或客户端必填项，不增加 Token.objects 的旧字段写入兼容层。仓库内部测试 fixture 直接适配新结构，不能用生产兼容魔法来掩盖旧 ORM 构造。

## 4. 发布与回退

发布需要短暂维护窗口：停止旧版本票据读取/签发/续期/撤销及清理进程，部署新代码并执行 `migrate`，完成旧票据读回检查后启动全部新版本实例。组合申请默认开启；需要暂缓或停止新格式申请时，可显式设置 `BKAPP_TOKEN_COMPOSITE_ENABLED=false`。

旧客户端 HTTP 协议兼容与旧服务进程数据库兼容是不同边界。删除旧列后不支持旧二进制继续连接该数据库；关闭组合申请开关不能替代数据库反向迁移。禁止在旧版本仍可能写入主表授权字段时执行回填和字段清理。

当前实现已包含 `permission.0006` 数据回填、`permission.0007` 结构清理、统一运行时读取和旧 HTTP 兼容测试。外部审查、当前提交 CI、发布和启用状态以 [PR #913](https://github.com/TencentBlueKing/BKFlow/pull/913) 及对应环境记录为准。

## 5. 验证

1. 真实 MySQL MigrationExecutor 从 `0004` 升级到最新：活跃和过期 Token、原值/时间不变、`001`、大小写和 Unicode、失效资源，恰好一条明细且旧列实际移除。
2. 从 `0005` 混合单项/组合升级：组合摘要及明细不变；异常组合中止，数据事务回滚，旧列仍在；重复正向函数执行不增条目或改变授权。
3. 最新版本反向到 `0005` 并再次正向：旧单项与新签发单项均正确还原/回填，多项保持完整，票据值和有效期不变。
4. 运行时单项也具有明细和摘要；旧单项申请复用已迁移票据，HTTP 成功/失败/混合输入/续期日期编码保持基线契约。
5. 全量接口回归、真实 MySQL 两连接并发、权限/插件/任务/template/auth、撤销 AND 和重复计数、hash/明细损坏拒绝、清理级联。
6. MySQL 并发及修改数据库结构的迁移用例在干净 pytest 进程中执行，后续套件排除已执行文件并合并覆盖率；不跳过实际 MySQL 验证。
7. 同步指南、原设计/计划、APIGW 文档/YAML/生成 zip 和权限规范的模型说明；原路由、认证、插件配置保持不变。新 HEAD CI 与本地测试结果分别报告。
