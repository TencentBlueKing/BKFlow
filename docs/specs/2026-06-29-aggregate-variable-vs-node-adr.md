# ADR: 并行变量聚合 — 选聚合变量类型而非聚合节点

- 日期：2026-06-29
- 状态：已采纳
- 关联：`docs/specs/2026-07-09-parallel-variable-aggregation-design.md`

## 背景

BKFlow 并行网关下，多分支用同一 key 输出会在扁平上下文池中相互覆盖。需要一种"聚合"机制收集各分支结果。两种方案：

- **方案 A — 独立聚合节点**：在汇聚网关后拖一个聚合插件节点，输入各源 key，输出合并结构
- **方案 B — 聚合变量类型**：把聚合下沉为变量本身的属性，多分支写同名 key 时变量升级为聚合类型，引擎自动累积

## 决策

**采纳方案 B（聚合变量类型）。**

## 理由

1. **去掉拓扑约束**：方案 A 强制"聚合节点必须在汇聚之后"，用户需理解控制流与数据流的先后；方案 B 把聚合变成数据属性，与节点摆放解耦。
2. **配置入口更自然**：用户本就在配置"节点输出到哪个全局变量"，顺手建立聚合关系，零额外步骤。
3. **复用引擎已有能力**：`extract_outputs` 中 `loop_enabled` 已实现 list 累积，方案 B 是把它从"循环节点专属"泛化为"变量属性触发"，改动有先例。
4. **交互更轻**：方案 A 要拖节点 + 配置；方案 B 只在设第二个同名输出时弹窗确认。

## 代价 / 权衡

- **类型升级成本**：单值变量升级为 list/dict 后，下游已有 `${result}` 引用需提示确认。这是方案 B 唯一比方案 A 多出的认知成本，通过"升级时高亮引用点 + 确认"控制。
- **并发 append**：两方案运行期都要面对 namespace + 并发收集底座；方案 B 同样需解决并行分支并发写同一聚合变量的原子性问题。

## 备选未采纳

- **方案 A（聚合节点）**：拓扑约束与额外节点概念使体验更重，否决为默认方案；未来如需复杂自定义聚合（reduce/脚本），可作为高级补充形态保留。
