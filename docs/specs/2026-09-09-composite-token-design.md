## 1. 目标与已确认约束

一个接入平台角色可能同时拥有模板调试、普通任务操作等不同资源上的能力。本设计让接入方通过现有 `apply_token` 接口申请一张包含多项授权的票据，页面和 SDK 仍携带一个 `BKFLOW-TOKEN`。

用户已确认：

1. 采用票据主表与授权明细表关联的方向。
2. 不新增接口，兼容旧版单项申请以及所有已有接口协议。
3. 第一版按整张票据撤销：撤销条件命中一项授权，就使该票据的全部授权失效。

首版不引入平台角色模型、单条授权撤销、给已发出票据追加授权、跨用户或跨空间票据、任意操作名称、批量返回多张票据。平台继续负责业务权限判断，BKFlow 继续定义资源与操作的含义。

本文件描述已实现行为与发布约束。验证覆盖及进度见[实现计划](../plans/2026-09-09-composite-token.md)；原枚举拆分的 94 个基线回归不单独作为组合能力验收证据。

## 2. 基线行为与实现改动范围

历史单项 [Token 模型](../../bkflow/permission/models.py) 以 `token` 为主键，并曾在主表保存资源三元组。[申请接口](../../bkflow/apigw/views/apply_token.py) 的旧 HTTP 输入与响应保持不变；[撤销接口](../../bkflow/apigw/views/revoke_token.py) 仍将匹配主票据的过期时间更新为当前时间。

以下消费者必须纳入适配，不能只修改 `Token.verify()`：

| 消费位置 | 当前用途 | 组合票据适配 |
| --- | --- | --- |
| `bkflow/permission/permissions.py` | 基础操作权限校验 | 查询票据的有效授权集合 |
| `bkflow/interface/task/permissions.py` | 任务、scope、模板调试任务校验 | 保留动作规则与资源继承，支持多项授权 |
| `bkflow/template/permissions.py` | 模板、调试与关联资源校验 | 同上 |
| `bkflow/interface/task/view.py` | 查询票据所属空间、任务 auth 汇总 | 空间仍来自票据主表，auth 来自授权集合 |
| `bkflow/template/serializers/template.py` | 模板 auth 汇总 | 合并全部有效票据的授权明细 |
| `bkflow/decision_table/permissions.py` | 读取票据授权 | 遍历匹配授权，保留模板/任务关联规则 |
| `bkflow/plugin/permissions.py` | 票据有效性与空间校验 | 使用公共票据检查，保留空间级权限语义 |
| `bkflow/pipeline_plugins/query/uniform_api/utils.py` | 通过 `get_resource_tokens()` 判断资源票据 | 支持关联明细且检查票据有效性 |
| `bkflow/permission/views.py`、`tasks.py`、`admin.py` | 续期、清理、管理展示 | 以主票据为生命周期单位 |

普通 APIGW 任务创建、执行入口继续使用原有应用与空间鉴权，不因这项改动新增资源票据要求。

## 3. 统一存储方案

原设计曾比较主表旧字段与授权明细并存的方案。最终实现选择全量自动回填并移除旧资源字段，所有票据只有一个权威授权来源；迁移与回退细节以[统一存储设计](2026-09-09-unified-token-storage-design.md)为准。

### 3.1 Token 主表

`Token` 保留 `token`、`space_id`、`user`、`expired_time` 和非空 `grant_set_hash`。主键和票据生成格式保持不变；集合摘要用于候选检索及完整性校验，不对外暴露。主表不再保存 `resource_type`、`resource_id` 或 `permission_type`。

### 3.2 TokenGrant 明细

| 字段 | 定义 |
| --- | --- |
| `id` | 独立主键 |
| `token` | 外键关联 Token，随主票据删除而级联删除 |
| `resource_type` | 与现有资源字段相同的字符串类型 |
| `resource_id` | 与现有资源 ID 相同的字符串类型，最长 32 位 |
| `permission_type` | `TokenPermissionType` 定义的操作字符串 |
| `grant_hash` | 单项规范三元组的 SHA-256 摘要，内部使用 |

逻辑上同一票据的三元组唯一，数据库通过 `(token, grant_hash)` 唯一约束落实，避免 MySQL 默认不区分大小写的排序规则将不同字符串三元组当成同一条记录。摘要冲突时必须核对完整三元组并拒绝不一致数据，不能据摘要合并不同授权。资源筛选使用 `(resource_type, resource_id, permission_type, token)` 索引；票据复用使用主表 `(space_id, user, grant_set_hash, expired_time)` 索引。索引名显式保持在数据库支持的长度内，需在项目支持的 MySQL 版本验证。

用户、空间和过期时间只保存在主表。单项票据恰好一条明细，多项票据有多条明细；明细无独立到期时间、撤销状态或权限追加接口。

### 3.3 授权集合的统一读取

权限模块提供统一的票据查找、授权集合读取、资源匹配和有效授权查询能力：

- 单项和多项票据都读取关联明细，在一次请求内复用读取结果，避免每种权限检查重复查库。
- 数据库查询 auth 或撤销对象时只从授权明细筛选，再对主票据去重；多个资源条件必须命中同一条明细。
- 明细缺失、重复、字段非法、单项摘要错误或完整集合摘要不一致时整张票据无效。
- 不将 Python 内部新增字段自动暴露为接口响应，也不新增 Token 查询接口或扩展现有无序列化器的 list/retrieve 入口。

## 4. apply_token：同一接口的两种输入

继续使用 `POST /space/{space_id}/apply_token/`，后端路由、HTTP 方法、operationId 和网关认证设置不变。用户名仍来自认证用户，空间仍来自 URL。任意授权都必须属于同一用户和同一空间。

### 4.1 旧版单项请求

```json
{
  "resource_type": "TEMPLATE",
  "resource_id": "100",
  "permission_type": "MOCK"
}
```

旧路径保持字段必填规则、DRF 字符串转换、choices、资源存在性校验、错误包装和额外字段忽略行为。模型虽然有 LABEL，申请仍不支持它；不在这次改动中收紧旧版已接受的资源与操作组合。

成功响应保持原字段集合。下面示例中的 token 为说明用值：

```json
{
  "result": true,
  "data": {
    "space_id": 1,
    "user": "alice",
    "resource_type": "TEMPLATE",
    "resource_id": "100",
    "token": "00000000000000000000000000000001",
    "expired_time": "2026-09-09T10:00:00Z"
  },
  "code": 0
}
```

不向旧响应增加 `grants`、`grant_set_hash` 或原本未返回的 `permission_type`；不强制补齐成功响应中原本没有的 `message`。可选 trace_id 与日期时间编码沿用当前响应链路。

### 4.2 新版组合请求

```json
{
  "grants": [
    {"resource_type": "TEMPLATE", "resource_id": "100", "permission_type": "MOCK"},
    {"resource_type": "TASK", "resource_id": "200", "permission_type": "OPERATE"}
  ]
}
```

规则：

1. `grants` 必须为非空列表，原始条目数最多 32，先检查条目数再去重。
2. 每项复用单项授权的字段校验与资源校验；不支持通配资源或省略资源 ID。
3. 完全相同的三元组去重，按三元组排序形成规范集合；保持原有资源 ID 字符串语义，不额外将 `001` 改写成 `1`。
4. 重复资源可以有不同操作，不进行权限包含关系压缩。例如 VIEW 与 EDIT 仍是两条显式授权。
5. `FLOW_*` 仍不是签发权限。资源与操作的组合限制沿用旧路径，成功签发不自动赋予未被权限类认可的能力。
6. 逐项校验的目标资源按 `(resource_type, resource_id)` 去重查询。任何一项失败，整体失败，既不创建票据也不续期已有票据。
7. 新输入使用既有错误包装和错误码类别，错误文案标明对应授权索引；不改变旧输入的字段名、错误顺序和包装方式。

新格式返回一张票据及完整规范授权集合：

```json
{
  "result": true,
  "data": {
    "space_id": 1,
    "user": "alice",
    "token": "00000000000000000000000000000002",
    "expired_time": "2026-09-09T10:00:00Z",
    "grants": [
      {"resource_type": "TASK", "resource_id": "200", "permission_type": "OPERATE"},
      {"resource_type": "TEMPLATE", "resource_id": "100", "permission_type": "MOCK"}
    ]
  },
  "code": 0
}
```

新响应不伪造一个顶层 `resource_type/resource_id` 代表整个集合。请求使用 grants、去重后仅剩一项时，允许复用或创建只有一条统一明细的票据，但响应仍使用 grants 结构。

### 4.3 输入识别与混合请求

为保留旧版忽略额外字段的行为，按以下顺序判断：

1. 顶层出现任意一个旧字段 `resource_type/resource_id/permission_type`，进入旧版序列化器。旧字段不完整时仍返回原必填错误；完整时按单项申请处理，额外 grants 不参与授权。
2. 没有任何旧字段、存在 grants 时，进入新格式。
3. 两类字段均未出现时，进入旧版序列化器，保持原缺参响应。

新接入方应只使用一种输入形式。文档明确混合输入的旧字段优先规则，不能静默把旧字段与 grants 取并集。网关 Schema 需描述该规则，但不额外开启网关请求体校验插件，以免旧请求的失败位置和错误响应发生变化。

## 5. 签发、复用与事务

单项申请按当前用户、空间和完整单项三元组匹配，继续优先返回最晚过期的有效票据，不把包含该项的多项票据交给单项申请者。

签发服务将规范授权集合序列化为带版本标识的确定性 JSON 后计算 SHA-256。摘要用于索引候选票据，复用前仍比较完整授权集合，并限制相同用户和空间。顺序变化、完全重复条目不影响复用；子集、超集、不同操作或不同资源不得复用同一张组合票据。

单项摘要输入为 `['v1', resource_type, resource_id, permission_type]`，集合摘要输入为 `['v1', 排序后的三元组数组]`；统一采用无额外空白、ASCII 转义的 JSON，再按 UTF-8 编码计算摘要。数据库筛选只是候选检索，鉴权中仍按原有资源匹配规则核对实际数据。

所有资源检查完成后才执行数据库事务。在事务内重新判断候选票据有效性，必要时创建主票据和全部明细。明细写入失败时整体回滚。外部 engine 资源查询放在事务之外，避免网络等待长期占用数据库锁。

复用仍遵循空间的自动续期开关；普通鉴权不触发续期。任何时候都不向已发出票据追加或替换授权。调用方的角色变化通过整票据撤销和重新申请表达。

首版保持旧版“并发申请可能生成多张等价票据”的边界，不承诺唯一签发。组合票据无论是否重复，都必须具有完整、正确且不可增权的授权集合。

## 6. 鉴权：完整条件检查后匹配授权

统一校验顺序：

1. 查询主票据，检查存在性、认证用户、可信空间上下文和当前有效期。
2. 读取该票据的唯一权威授权集合。
3. 按当前动作允许的权限规则，对每条完整授权执行资源匹配。
4. 只要有一条授权独立满足当前动作即可通过。若某个接口本身要求多项条件，继续逐项检查其原有条件。

例如 `TEMPLATE/100/MOCK` 与 `TASK/200/OPERATE` 不得组合生成 `TEMPLATE/100/OPERATE` 或 `TASK/200/MOCK`。两项授权中的资源类型、ID 和操作不可交叉拼接。

保留既有资源语义：

- 模板票据精确匹配模板。
- 任务票据按现有父任务关系支持后代，子票据不反向授权父任务。
- 模板 MOCK 访问调试任务时继续检查 create_method 与所属模板，不自动覆盖普通任务。
- scope 按目标资源的 scope 属性匹配，不转换成全空间授权。
- EDIT/OPERATE/MOCK 对 VIEW 等动作的包含关系仍由各权限类决定，不新增全局权限等级。

scope 校验需要明确实际目标是 TEMPLATE 还是 TASK，避免两个资源使用相同数值 ID 时读取错误对象。由内部调用方传递目标类型，不向旧 HTTP 接口增加必填字段。保留 `Token.verify()` 现有调用形式，扩展内部上下文时使用可选参数并迁移仓库调用点。

所有已知 HTTP 调用点必须提供其目标类型。没有目标类型的旧式内部 SCOPE 调用，仅对单项票据保留原回退顺序；多项票据不能猜测目标类型，缺失时拒绝该 scope 授权分支。

对插件空间查询、决策表、Uniform API 等绕开 `Token.verify()` 的路径，统一公共票据有效性和身份/空间检查，再保留各自资源规则。Uniform API 的“同时存在 template_id 和 task_id 时模板优先”规则不变。`get_resource_tokens()` 仍返回票据 QuerySet，供现有 `.exists()` 调用使用；相同票据不能因多条匹配明细重复返回。

这部分修正与组合票据的用户、空间及整票据失效保证直接相关。它会拒绝此前辅助路径错误接受的过期、错用户或错空间票据；不新增接口参数，不调整模板发布等其他动作的权限映射。

## 7. revoke_token：筛选授权，撤销整票据

继续使用 `POST /space/{space_id}/revoke_token/`，请求字段和返回字符串结构不变。不增加 grants 或撤销模式参数。

匹配逻辑为：

`票据空间匹配 AND token/user 条件匹配 AND 存在一条满足全部资源条件的授权`

只有资源相关条件存在时，才要求匹配授权；没有资源条件时直接筛选主票据。所有票据的资源条件都必须落在同一条明细上。

| 请求条件 | 行为 |
| --- | --- |
| 只有 token | 撤销该空间内这张票据的全部授权 |
| 只有 user | 撤销该空间内该用户的所有票据 |
| 资源类型、ID、操作等任意组合 | 查找存在完整匹配授权的票据，撤销整张票据 |
| token/user 与资源条件同时存在 | 全部条件 AND 匹配后撤销整张票据 |
| 空对象 | 沿用旧协议，撤销该空间全部票据 |

例：票据含 `TEMPLATE/100/MOCK` 和 `TASK/200/OPERATE`。按 `TEMPLATE/100/MOCK` 撤销会同时使任务授权失效；按 `TEMPLATE/200` 撤销不会命中它。

撤销只进行授权字段的精确筛选，不按 scope 成员、父子任务或权限包含关系扩展过滤。VIEW 条件不会匹配 EDIT 明细。

事务内对匹配的主票据进行更新，过期时间设为当前时间，不删除明细。返回仍为 `N tokens revoke success`，N 统计匹配并更新的不同主票据数量，不统计明细数量；沿用旧协议，已过期票据也计入匹配数量。

## 8. 续期、过期与清理

继续使用 `POST /api/permission/token/{token}/renewal/`，前端请求、空间自动续期开关以及既有返回包装和 expired_time 字段不变。成功续期只更新主表过期时间，作用于全部授权。成功 JSON 的 expired_time 继续按服务默认时区输出不带偏移的时间；关闭续期开关时保留数据库原时间编码，活动时区不改变成功分支的旧协议。内部判断使用带时区时间。

为使“整张票据失效”可靠，续期不能继续依赖类定义时固定的时间过滤。查询必须使用请求时刻，续期在锁定主票据后重新检查有效期与用户；申请过程中的自动续期也使用相同更新规则。有效票据的到期时间严格晚于当前时间，撤销后不得通过续期恢复。

MySQL 验证发现通过有效期二级索引直接 `SELECT FOR UPDATE` 会与主行锁后的有效期更新形成死锁。因此，复用与撤销先普通查询发现候选，再仅按主键集合、主键顺序批量持锁，并在锁后重新核对身份、空间、有效期及授权/过滤条件；复用继续选择最晚过期的有效候选。

续期与撤销并发通过主票据行锁协调：续期先完成时，后续撤销覆盖它；撤销先完成时，续期不能延长已失效票据。第一版不需要独立的授权撤销状态；时间字段仍承载整张票据的失效结果。

旧请求和正常响应协议保持兼容；过期/撤销票据被旧实现续活的缺陷不作为兼容目标。这是生命周期正确性修正，需要单独覆盖负向和并发测试，不得只验证续期成功路径。

过期清理仍按既有周期及 TOKEN_RETENTION_TIME 筛选主票据；删除主票据时级联清理授权明细。撤销和清理都不终止已经运行的引擎任务。

## 9. auth 与前端兼容

模板和任务详情继续按当前用户、空间、相关资源及有效期汇总所有有效票据，输出去重后的扁平字符串数组。管理员默认数组的内容和顺序保持不变。

- 模板与 scope 的展示规则延续当前实现。
- 任务详情中的模板权限继续映射为 FLOW_*；历史非标准组合的前缀响应也保持兼容。
- 多张票据包含相同权限时只显示一次；不把 grants 对象直接返回到 auth。
- auth 仍是用户持有票据的权限汇总，不替代当前请求所携带票据的鉴权。
- 前端 URL、Cookie、请求头和续期入口不变，无需在浏览器中维护多张票据或进行逐动作切换。

## 10. 旧协议兼容矩阵

| 场景 | 要求 |
| --- | --- |
| 旧单项申请成功 | 字段集合、字段类型、时间编码、返回包装保持一致 |
| 旧单项申请失败 | 参数校验、认证、资源不存在的响应类别和包装保持一致 |
| 旧请求携带额外字段 | 继续忽略，不改变签发用户或空间；混合 grants 按第 4.3 节处理 |
| 旧票据继续访问页面/SDK | 原值可用，无需重签；受原资源范围和当前有效期约束 |
| 旧单项重复申请 | 继续复用匹配的有效单项票据，并按配置决定是否续期 |
| 旧撤销请求 | 原过滤字段、AND 语义、整票据失效和响应计数单位不变 |
| 旧续期请求 | URL、方法、输入、正常响应包装及有效期配置不变 |
| 模板/任务 auth | 维持字符串数组、FLOW_* 投影和管理员默认集合 |
| 普通 APIGW 任务 API | 不额外要求 BKFLOW-TOKEN |
| 非法、过期、错用户/空间票据 | 依照第 6、8 节拒绝错误放行，不将实现缺陷固化为协议 |

兼容性指已有客户端协议和受支持的授权行为。删除旧资源字段后，旧版本服务进程不能继续连接迁移后的数据库；HTTP 兼容不表示新旧实例可以混跑。

## 11. 迁移、启用与回退

发布通过 `permission.0006` 自动校验并回填全部历史单项，再由 `permission.0007` 删除主表旧资源字段并将集合摘要改为非空。票据值、用户、空间、有效期和原授权三元组不变，不批量重签。三个旧字段全空会在任何数据变更前停止；未知枚举或部分空字段按原值迁移，但运行时继续拒绝非法明细。

服务配置 `TOKEN_COMPOSITE_ENABLED` 默认开启，只控制 grants 格式的申请入口；显式设置 `BKAPP_TOKEN_COMPOSITE_ENABLED=false` 可关闭。旧格式申请始终可用；关闭开关不停止读取、鉴权、撤销和续期已经发出的多项票据。关闭时 grants 格式返回既有错误包装中的功能未启用提示。

上线顺序：

1. 进入维护窗口，备份数据库，并停止旧版本票据读取、签发、续期、撤销和清理进程。
2. 部署新代码并执行普通 `migrate`；异常必须停止在旧字段清理之前，明确处理数据后再重试。
3. 读回旧票据并启动全部新版本实例，保持组合申请关闭，验证旧客户端路径。
4. 环境验收通过后再开启组合申请，验证同一张票据的跨资源操作与整票据撤销。

明确支持最新版本反向迁移到 `permission.0005`：结构迁移恢复旧列，数据迁移将有效单项明细还原为旧三元组并清除其摘要，多项票据保持 `0005` 组合存储。若继续回退到不支持组合票据的旧二进制，须先使所有多项票据失效并另行验证更早迁移链路；关闭申请开关不能替代数据库反向迁移。部署兼容与实际版本覆盖属于上线验收，不以本地测试代替。

## 12. 文档和网关同步

实现时同步更新 [apply_token 文档](../../bkflow/apigw/docs/zh/apply_token.md)、[revoke_token 文档](../../bkflow/apigw/docs/zh/revoke_token.md)、[Token 接入指南](../guide/token_authorization.md)和 `api-resources.yml` 中对应既有 operation 的输入输出 Schema。

路由、operationId、后端映射及认证设置保持不变。旧格式 Schema 继续描述原响应；grants 格式单独描述新响应，保留额外字段规则。通过 `bash scripts/apigw_docs.sh` 重新生成并校验文档包，不手动编辑 zip，也不借机同步其他网关资源。

## 13. 验证与验收

| 验证组 | 必须覆盖 |
| --- | --- |
| 旧协议回归 | 旧 apply/revoke/renew 请求和响应快照、额外字段、资源 ID 转换、错误包装、认证失败、日期编码、auth 默认集合 |
| 单项兼容 | 真实迁移后的历史票据；旧格式新建/复用；grants 单项与旧格式共享单项票据但按请求格式响应 |
| 组合签发 | 两项授权、同资源多操作、顺序变化、去重、完整集合复用、子集/超集不复用、同用户同空间限制 |
| 输入边界 | 空/null/非列表 grants、超过 32 项、缺字段、FLOW_*、LABEL、无效资源、混合旧字段与 grants |
| 事务完整性 | 任一资源失败或明细写入失败无部分票据；非法集合不续期已有票据；并发重复票据各自完整 |
| 授权隔离 | 跨授权拼接拒绝、错用户/空间/资源/操作拒绝、缺失/损坏明细拒绝 |
| 资源继承 | 模板与任务同 ID、scope 中不同资源类型、父子任务方向、MOCK 与普通任务边界、既有动作权限规则 |
| 辅助接口 | 决策表各动作、插件空间检查、Uniform API 资源选择、过期和身份/空间约束 |
| 整票据撤销 | 任一明细命中即全部失效；条件必须命中同一明细；主字段与资源条件 AND；空筛选；精确权限筛选；主票据去重计数 |
| 生命周期 | 有效期边界、续期开关、用户一致性、撤销后续期拒绝、申请复用与撤销竞争、清理级联 |
| 前端/SDK | 同一 token 调试模板并操作普通任务，auth 字符串兼容，撤销后两类调用均被拒绝 |
| MySQL | 自动生成迁移实跑、新旧记录混合、索引/唯一约束、大小写不同的资源字符串与摘要一致性、真实连接的续期与撤销并发、事务回滚及级联删除 |
| 交付检查 | 文档示例与相对链接、网关包与源码一致、既有路由与 operationId 不增加、格式检查和相关回归 |

先为旧协议建立基线契约测试，再增加组合授权和负向用例。SQLite 可用于快速单测；MySQL 的迁移、约束和并发验证必须单独完成，不以 SQLite 或 mock 行锁的结果替代。已完成设计确认与实现；本地 MySQL 测试和迁移证据不能代替 CI、真实部署版本或业务验收。
