# 组合 Token 接入改造指南（BKFara 等接入平台）

本文供接入方后端、前端和测试开发使用，目标是让同一个业务角色可以通过一张 BKFlow Token 同时访问多个资源、执行不同操作。

适用版本：包含 [PR #913](https://github.com/TencentBlueKing/BKFlow/pull/913) 的组合申请、统一授权存储及默认开启配置的 BKFlow 部署。上线前应确认目标环境已完成升级和迁移；不能仅凭代码已提交判断环境已支持。本指南按 BKFlow 实际接口编写，BKFara 的模块名、角色名和资源 ID 均为改造示例，不表示已核查或修改 BKFara 仓库。

## 1. 接入方需要做什么

旧单项申请和存量 Token 继续兼容，仅使用单项权限的接入方不必立即改造。需要组合权限时，按下表修改：

| 改造位置 | 需要落实的行为 |
| --- | --- |
| 后端角色授权映射 | 将业务角色映射为授权三元组列表，逐项确认当前用户的业务权限 |
| 后端 Token 申请封装 | 调用原 `apply_token`，请求体使用 `grants`，不混入顶层旧字段 |
| 响应解析 | 新格式读取 `data.grants`，不再要求顶层 `resource_type/resource_id`；保留旧格式解析 |
| Token 缓存和登记 | 按环境、应用、用户、空间及完整授权集合区分缓存，并登记已发出票据用于撤销 |
| 页面/SDK 传递 | 继续传一个 Token；换资源、用户或授权集合时使用对应的新票据 |
| 角色变更与退出处理 | 清理相关缓存，并按业务策略撤销所有受影响票据；第一版撤销整张票据 |
| 错误与续期处理 | 同时检查 HTTP 和业务结果；续期失败不能视为授权仍然有效 |
| 联调测试 | 使用普通用户验证允许、拒绝、跨用户/空间隔离及整张撤销 |

接入方无需访问 BKFlow 的 Token 数据表，无需参与数据库迁移，也无需把同一个 token 值重复保存为多张 BKFlow 票据。存量数据由 BKFlow 发布迁移处理，原 token 值、用户、空间和有效期保持不变。

## 2. 将业务角色映射为授权集合

例如，用户 `alice` 在空间 `3` 的某个业务角色具有以下权限：

| 平台侧业务权限 | BKFlow 授权 |
| --- | --- |
| 调试模板 `100` | `TEMPLATE / 100 / MOCK` |
| 查看并操作普通任务 `200` | `TASK / 200 / OPERATE` |

角色名称留在接入方，BKFlow 只接收资源和操作。上面两项可以申请为一张票据 T1；T1 不能访问模板 `101` 或无关任务，也不会把两条授权拼成 `TEMPLATE / 100 / OPERATE`。

常用映射如下。权限包含关系由具体接口实现，不能当作所有接口通用的等级体系。

| 需求 | 建议申请 |
| --- | --- |
| 查看模板 | `TEMPLATE / 模板ID / VIEW` |
| 编辑模板 | `TEMPLATE / 模板ID / EDIT` |
| 调试模板 | `TEMPLATE / 模板ID / MOCK` |
| 查看任务 | `TASK / 任务ID / VIEW` |
| 查看、操作任务 | `TASK / 任务ID / OPERATE` |

注意以下边界：

- `TEMPLATE/MOCK` 包含较强的调试能力，并可访问、操作该模板创建的 MOCK 任务；不会自动授予普通任务操作权限。调试可能执行真实引擎任务。
- `TASK/OPERATE` 可查看和操作目标任务，也可沿父子关系覆盖其后代任务；子任务票据不能反向授权父任务。
- `FLOW_VIEW/FLOW_EDIT/FLOW_MOCK` 是任务详情 `auth` 的展示标记，不能作为 `permission_type` 申请。
- 不要为了拼接权限直接扩大到 `SCOPE/MOCK`。SCOPE 按资源当前作用域生效，范围可能随资源迁入、迁出变化；只有平台角色本就拥有该作用域权限时才使用。
- 当前申请支持 `TEMPLATE/TASK/SCOPE`，不支持 `LABEL`。SCOPE ID 为 `scope_type_scope_value`，要求恰好一个下划线，且空间内已存在相同作用域的模板。
- 模板发布、回滚、批量任务等动作仍须逐接口联调；不能仅凭上表推断所有写动作的限制。具体边界见 [Token 授权说明](token_authorization.md#9-当前实现边界)。

**业务权限必须在接入方后端检查。** BKFlow 不会查询 BKFara 的角色系统；不能直接把浏览器提交的任意 `grants` 转发出去。网关调用和嵌入页面的登录用户名应与被授权用户一致，不能用公共服务账号申请后分发给其他登录用户。

## 3. 修改申请接口封装

### 3.1 沿用原接口和认证方式

网关资源路径：`POST /space/{space_id}/apply_token/`。沿用接入方已有 BKFlow 网关地址和认证客户端；这里的路径不是页面域名下的 `/api/...` 地址。

申请仍要求网关应用认证、用户认证和接口访问权限，调用应用必须绑定目标空间。`space_id` 来自 URL，用户名来自认证身份；请求体的 `user` 或 `space_id` 不能替代它们。应用密钥、用户认证材料不要发送到 iframe URL。

以下示例均为业务请求体，不包含网关认证材料。

旧单项请求可以继续使用：

```json
{
  "resource_type": "TEMPLATE",
  "resource_id": "100",
  "permission_type": "MOCK"
}
```

组合请求改为：

```json
{
  "grants": [
    {"resource_type": "TEMPLATE", "resource_id": "100", "permission_type": "MOCK"},
    {"resource_type": "TASK", "resource_id": "200", "permission_type": "OPERATE"}
  ]
}
```

规则：

1. 顶层出现任意 `resource_type/resource_id/permission_type` 时，服务端优先按旧格式处理，`grants` 会被忽略；旧字段不完整时返回旧必填错误。组合请求只传 `grants`。
2. `grants` 为非空列表，原始条目数为 1–32；即使条目重复，超过 32 项也拒绝。每项三个字段均必填，资源 ID 最长 32 个字符。
3. 使用字符串资源 ID，不自行转成整数、改变大小写或去掉前导零。按 BKFlow 返回的真实 ID 构造授权。
4. 全部资源必须在目标空间存在；任意一项失败，整次申请失败，不创建部分授权，也不续期已有候选票据。
5. 不支持为 T1 追加授权。需要增加或减少授权时，按完整目标集合重新申请；收回旧权限还需撤销相关旧票据。

### 3.2 任务尚未创建时

`TASK` 授权必须使用已经存在的任务 ID。如果用户先打开模板、随后创建普通任务：

1. 打开模板时，按当前需求申请模板单项票据。
2. 普通任务创建继续走平台已有的后端 APIGW 调用及业务权限检查，不要将模板 Token 当作普通任务创建权限。
3. 拿到真实任务 ID 后，再申请“模板授权＋该任务授权”的完整集合。
4. 打开任务页时传入新返回的 Token。原模板票据没有被自动扩权，也没有被自动撤销。

不要用占位任务 ID 预先签发，不要将一项校验失败当成申请其他项成功。

### 3.3 解析成功响应

新格式示例：

```json
{
  "result": true,
  "data": {
    "space_id": 3,
    "user": "alice",
    "token": "<BKFLOW_TOKEN>",
    "expired_time": "2026-09-09T12:00:00Z",
    "grants": [
      {"resource_type": "TASK", "resource_id": "200", "permission_type": "OPERATE"},
      {"resource_type": "TEMPLATE", "resource_id": "100", "permission_type": "MOCK"}
    ]
  },
  "code": 0
}
```

`<BKFLOW_TOKEN>` 是占位符，实际为一个 32 位字符串。授权列表会去重、排序，响应顺序不必与请求一致。接入方应确认响应用户、空间和完整集合符合本次申请，成功响应不保证包含 `message`。

新旧响应差异：

| 字段 | 旧单项请求的响应 data | 新 grants 请求的响应 data |
| --- | --- | --- |
| `token/user/space_id/expired_time` | 保留 | 保留 |
| 顶层 `resource_type/resource_id` | 有 | 无 |
| 顶层 `permission_type` | 无，沿用申请时保存的值 | 无，从各条 grants 读取 |
| `grants` | 无 | 有，即使去重后只剩一项 |

单项 grants 请求可能与旧单项请求复用同一个 Token，但响应格式仍跟随本次请求。不要根据 Token 值是否变化推断授权变化，也不要要求重复申请必定返回同一个值；并发时可能出现多张等价票据。

## 4. 调整缓存与权限变更处理

缓存不能只用“用户名＋角色名”或“模板 ID”作为键。以下是接入方缓存键的伪代码，不是 BKFlow SDK 接口，也不需要复刻服务端摘要算法：

```python
normalized_grants = tuple(sorted({
    (g["resource_type"], g["resource_id"], g["permission_type"])
    for g in authorized_grants
}))
cache_key = (
    deployment_id, app_code, space_id, username,
    policy_revision, normalized_grants,
)
```

`authorized_grants` 必须是后端业务鉴权后的结果；`policy_revision` 是平台自身角色/授权策略的版本，平台没有该字段时应使用自己的权限变更失效机制。

- 缓存内容至少保存 Token、用户、空间、完整 grants、服务端到期时间。可设置小于服务端有效期的缓存期限，但不要将 Cookie 存活时间当作授权期限。
- 命中缓存前仍需确认当前用户具有这些业务权限。新增用户、切换空间、切换环境或授权集合变化时不能沿用原缓存。
- 服务端只按相同完整集合复用；不要把更大集合的票据当作子集请求的缓存结果，也不要把多张 Token 的字符串或授权拼成一张。
- 同一角色在不同任务页面可以生成不同集合，无需把该角色能访问的所有任务一次性塞入票据。超过 32 项时重新划分实际页面场景；只有已有作用域授权时才考虑 SCOPE。
- 登记已发出票据和授权集合，便于定位所有受影响的旧票据。清除缓存、更新策略版本或停止续期，都不会立即使服务端旧票据失效。

角色降权时建议按以下顺序处理：先更新平台权限并阻止旧权限继续签发，定位并撤销所有包含被收回权限的票据，清理相关缓存，再按剩余权限重新申请。需要协调同时发生的签发与角色变更，避免撤销完成后又发出依据旧权限计算的票据。

不要只撤销当前浏览器中的 T1：其他页面、会话或并发申请可能拿到其他等价票据。若无法精确登记，可按明确的用户/空间范围撤销，但要接受该用户同空间其他页面也需要重新申请的影响。

## 5. 页面与 SDK 传递

前端仍只传一张 Token，无需自行拆解 grants 决定每次请求用哪张票据。

现有 iframe 入口保留 `token` query 参数。以 `BKFLOW_SITE_URL` 表示已有页面根地址（含实际部署前缀），可使用以下已有路由：

```text
<BKFLOW_SITE_URL>/template/edit/100/?space_id=3&token=<BKFLOW_TOKEN>
<BKFLOW_SITE_URL>/taskflow/execute/3/?instanceId=200&token=<BKFLOW_TOKEN>
```

路径拼接时避免重复 `/`，使用 URL 编码处理参数。模板调试页继续使用当前接入已有的调试路由，不必因组合票据更换页面入口。

BKFlow 页面首次初始化会读取 URL Token，写入页面状态与 `bkflow-token` Cookie，之后接口请求携带 `Bkflow-TOKEN` 请求头；Token 不能替代登录态。SDK 或自建页面调用需要资源票据的接口时，继续传同名请求头，并保留该接口原有认证要求。

**在已加载的 iframe 内更换票据时，要重新初始化页面。** 当前页面只在首次初始化读取 query Token；仅修改同一个 SPA 的路由 query，可能继续使用旧状态。接入方可销毁并重建 iframe，再用新 URL 加载。不要依赖同域 Cookie 替所有已打开页面同步切换票据，尤其是多页面、不同资源或切换账号场景。

`auth` 仍为字符串数组，例如 `OPERATE/FLOW_MOCK`。它汇总当前用户持有的相关有效票据，并不保证当前请求携带的这一张 Token 具备全部展示能力。后端返回了新 Token 后，页面必须实际使用它；不能只刷新按钮展示。

普通后端 APIGW 任务接口与嵌入页面/SDK 资源接口的认证职责不同。不要给所有网关调用统一增加“只凭 BKFLOW-TOKEN 放行”的逻辑。

## 6. 续期与撤销

### 6.1 续期

页面续期仍为 `POST /api/permission/token/{token}/renewal/`，这是 BKFlow 页面服务接口，需要当前用户登录态，不是新增网关接口。已有 BKFlow 编辑/调试页面的续期机制可继续使用。

- 普通业务请求不会自动续期。再次申请同一集合时，是否刷新有效期取决于空间 `token_auto_renewal` 配置。
- 续期作用于整张票据，不会修改 grants。已过期或撤销的 Token 不能续活；需要重新检查业务权限后申请。
- 续期响应存在外层请求结果和 `data.result`，外层成功不代表续期成功。自建续期封装应同时检查两层，并使用返回的真实到期时间。
- 申请响应应按返回值的时区信息解析；续期成功响应沿用旧协议，可能是服务默认时区的不带偏移字符串。自建客户端应按已约定的服务时区解析，不能一律按 UTC 解释。
- 对申请结果不确定的调用，可以按相同集合重试，但不能把它当作严格幂等、一定只产生一张票据的接口。

### 6.2 撤销整张票据

沿用网关资源 `POST /space/{space_id}/revoke_token/`。精确撤销 T1：

```json
{
  "token": "<BKFLOW_TOKEN>"
}
```

成功响应：

```json
{
  "result": true,
  "data": "1 tokens revoke success",
  "message": "",
  "code": 0
}
```

第一版撤销的是整张 T1，模板调试和任务操作两项一起失效。若角色还应保留任务操作权限，应重新申请只包含剩余授权的票据。

撤销接口也支持 `user/resource_type/resource_id/permission_type` 过滤。资源条件必须命中同一条明细；命中后整张票据失效。要撤销 `alice` 对模板 `100` 的所有直接模板授权，可使用：

```json
{
  "user": "alice",
  "resource_type": "TEMPLATE",
  "resource_id": "100"
}
```

这里省略 `permission_type`，避免只撤销 VIEW 而遗漏 EDIT/MOCK。过滤不会展开 scope 成员、父子任务或权限包含关系；上述请求不能撤销通过 SCOPE 获得的模板访问权限。必须结合平台登记的完整 grants 查找相关票据，或选择业务允许的更宽撤销范围。

撤销接口需要应用认证和接口权限，不要求网关用户认证；请求体 `user` 是撤销对象过滤条件，与申请接口不同。**不要提交空对象 `{}`，它会撤销 URL 空间的全部票据。** 返回数量是主票据数，包含已过期记录，不是授权条目数。退出平台不会自动撤销 Token；撤销也不会终止已运行任务。

## 7. 错误处理与兼容部署

| 场景 | 接入方处理 |
| --- | --- |
| HTTP 200，但 `result=false` 或 `code` 非零 | 视为失败，不读取/缓存 `data.token`；不要仅判断 HTTP 状态 |
| `grants` 为空、超过 32 项、字段非法 | 修正请求，保留错误中的条目索引供排查，不反复重试相同参数 |
| 资源不存在或不属于目标空间 | 核对资源创建结果及平台映射；不删除失败项后静默申请其余权限 |
| 新格式申请未启用，或环境仍为旧版本 | 明确提示当前环境不支持该组合场景；单项场景可按已配置兼容策略使用旧协议 |
| 网关认证/空间应用校验失败 | 按原认证链路排查；不要替换为其他用户、管理员或更大 scope 来绕过 |
| 页面因过期、撤销或权限不足被拒绝 | 先检查登录用户和当前业务权限，再决定是否重新申请；不要对所有 403 无限重试 |
| 续期外层成功、`data.result=false` | 按续期失败处理，不能假定已延长有效期 |

部分业务错误沿用 HTTP 200 包装，参数错误常见 `code=400`，资源错误或开关关闭常见 `code=500`；网关拒绝等也可能直接返回非 2xx。错误文本可能变化，不要依赖中文 message 识别环境能力。应由部署配置或联调约定确定是否启用组合申请。

默认开启仅指新版本在未设置环境变量时的行为。已有环境显式设置 `BKAPP_TOKEN_COMPOSITE_ENABLED=false` 时仍关闭。关闭该开关只停止 grants 格式申请，已有组合票据仍可鉴权、续期和撤销；接入方也需要停止新的组合入口并处理缓存，而不是将开关当作全部票据失效操作。

旧单项接口继续兼容，但不应将组合请求失败自动降级成“只申请第一项”，也不能批量申请多张旧 Token 后假装得到同一张组合票据。

## 8. 上线顺序与验收

1. BKFlow 维护方完成新版本部署和自动迁移，确认服务全部运行新代码；接入方不执行 BKFlow 数据库迁移。
2. 接入方后端上线角色映射、组合申请、缓存与撤销改造，保留旧单项通道；确认目标环境没有显式关闭组合入口。
3. 前端上线新票据传递及重新初始化页面逻辑，使用普通用户跑通下表；不要用管理员的访问成功替代验收。
4. 先选择一个真实业务角色和一组模板/任务验证，再扩大使用范围。问题定位应记录环境、用户、空间、资源、请求格式和 trace_id，避免将完整 Token 或认证材料写入共享日志。

| 验收项 | 预期结果 |
| --- | --- |
| 旧单项请求与升级前的有效旧 Token | 请求/响应保持兼容，原 Token 可继续访问其授权资源 |
| `TEMPLATE/100/MOCK + TASK/200/OPERATE` | 同一 Token 可调试模板 100、操作普通任务 200 |
| 无关模板/任务、错误用户、错误空间 | 被拒绝；模板 MOCK 不会单独授权普通任务操作 |
| 只有一项 grants | 返回 grants 格式，仍可按原资源范围访问 |
| grants 顺序调整或重复 | 返回规范化后的等价集合；不要求并发时 Token 值唯一 |
| 顶层旧字段混入 grants | 按旧协议处理；接入封装应避免构造此请求 |
| 一项资源无效、空数组、33 项 | 整次申请失败，不产生部分票据 |
| 先打开模板，再创建普通任务 | 创建后按真实任务 ID 重新申请组合，任务页使用新票据 |
| 切换角色/资源、多个 iframe、刷新页面 | 每个页面实际请求携带正确票据，不借用其他页面 Cookie |
| Token 到期、撤销后续期 | 不恢复授权；重新申请前重新执行平台业务鉴权 |
| 按 token 或一项资源条件撤销 | 整张票据全部能力失效；保留能力需要重新申请 |
| 角色降权且存在多张等价/关联票据 | 所有受影响票据被处理；只清缓存不算完成撤权 |
| SCOPE 资源与相同数值 ID 的模板/任务 | 按目标资源的实际 scope 判断，无错误跨类型放行 |
| 关闭组合开关 | 新格式申请失败，旧单项申请和已有票据消费保持既有行为 |

## 9. 接入方交付内容

交付时附上角色到 grants 的映射表、申请/解析封装改动、缓存键与失效策略、票据登记与撤销策略、页面换票方式，以及上述验收记录。示例中的空间、用户名和资源 ID 应替换为联调环境真实值。
